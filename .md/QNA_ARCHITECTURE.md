# QNA — 전용 설비 회수 아이템

각 질문의 `답변:` 뒤에 선택지를 하나 적어 주세요. 하나의 질문은 하나의 결정만 다룹니다.

## 확정 전제

- 배치된 설비 액터와 회수 후 월드에 생기는 아이템 액터는 서로 다른 클래스와 인스턴스입니다.
- 기존 Q 홀드 입력, 설비별 회수 가능 조건, 드롭 위치 계산, 충돌 사전 검사와 실패 롤백 경로는 유지합니다.
- 회수 성공 시 자동으로 손에 들지 않고 설비가 있던 자리에 힘을 주지 않은 물리 아이템으로 생성합니다.
- 플레이어가 이미 소지한 물건은 회수 성공 여부와 무관하게 유지합니다.
- 최초 회수 아이템 표시는 Unreal Engine 기본 Cube 메시를 사용합니다.
- 설비 회수 아이템은 이번 범위에서 `FreeDrop`만 지원하며 exact fixed-slot 보관은 구현하지 않습니다.
- 설비 회수 아이템도 일반 아이템처럼 `HeldTransform`의 위치와 회전만 적용하며 Scale은 무시합니다.

## Q89. 설비 회수 아이템 클래스는 어떻게 구성할까요?

- A: 공통 네이티브 `APlaceableFacilityItemActor` 하나를 만들고 설비 Definition으로 종류를 구분
- B: 세탁기·건조기·목욕탕·락커마다 네이티브 회수 아이템 클래스를 별도로 구현
- C: 네이티브 공통 기반만 만들고 설비마다 Blueprint 회수 아이템 클래스를 반드시 제작
- 권장안: A — 현재 차이는 데이터로 표현할 수 있으므로 클래스 중복 없이 전용 회수 아이템 계약을 분리할 수 있습니다.
- 답변: A

## Q90. 배치 설비 클래스와 회수 아이템 클래스의 대응 정보는 어디에 둘까요?

- A: `UFacilityPlacementDefinition`이 `PlacedFacilityClass`와 `RecoveryItemClass`를 함께 소유
- B: 배치 설비는 회수 아이템 클래스를, 회수 아이템은 배치 설비 클래스를 서로 직접 참조
- C: 별도 Subsystem이 클래스 대응표를 소유
- 권장안: A — 양방향 참조 불일치를 막고 배치 Definition을 단일 변환 정보 원본으로 유지할 수 있습니다.
- 답변: A

## Q91. 배치 설비를 회수 아이템으로 바꾸는 트랜잭션 순서는 어떻게 할까요?

- A: 새 아이템을 지연 생성해 데이터와 물리를 검증한 뒤 설비 등록을 해제하고, 성공이 확정된 마지막에 원본 설비를 파괴
- B: 원본 설비를 먼저 파괴한 뒤 회수 아이템 생성을 시도
- C: 원본 설비를 숨겨 보존하고 별도 아이템을 생성
- 권장안: A — 생성 실패 시 원본 설비를 그대로 유지할 수 있어 손실과 복제를 함께 막습니다.
- 답변: A

## Q92. 회수 아이템을 다시 배치 설비로 바꾸는 트랜잭션 순서는 어떻게 할까요?

- A: 새 설비를 지연 생성해 초기화·등록까지 성공시킨 뒤 회수 아이템을 제거
- B: 회수 아이템을 먼저 제거한 뒤 새 설비 생성을 시도
- C: 회수 아이템 액터 자체를 배치 설비 상태로 전환
- 권장안: A — 배치 실패 시 기존 아이템과 프리뷰 상태를 유지하며 별도 클래스 원칙도 지킬 수 있습니다.
- 답변:A

## Q93. 설비와 회수 아이템 사이에 어떤 데이터를 전달할까요?

- A: `FFacilityPlacementPayload`로 Definition과 배치에 필요한 영속 인스턴스 값만 전달
- B: Definition만 전달하고 모든 인스턴스 값은 기본값으로 재생성
- C: 원본 액터의 전체 속성을 직렬화해 전달
- 권장안: A — 비어 있어야 회수 가능한 런타임 내용물·이용 상태는 제외하면서 필요한 설정만 명시적으로 보존합니다.
- 답변: A

## Q94. 회수 아이템의 외형과 공통 크기·소지 위치는 어디에서 설정할까요?

- A: Definition에는 설비별 `RecoveryItemMesh`만 두고 공통 클래스의 Root Static Mesh Component Scale과 `HeldTransform`을 사용
- B: Definition이 메시, `RecoveryItemVisualScale`과 `HeldTransform`을 모두 설비별로 소유
- C: 설비별 Blueprint가 메시, `RecoveryItemVisualScale`과 `HeldTransform`을 소유
- 권장안: A — 같은 규격의 직육면체에 설비별 그림만 다르게 사용한다는 현재 표현 정책과 일치합니다.
- 답변: A. 설비별 Definition에는 서로 다른 그림이 적용된 같은 크기의 직육면체 `RecoveryItemMesh`를 지정한다. 별도 `RecoveryItemVisualScale`은 두지 않고 `APlaceableFacilityItemActor`의 Root Static Mesh Component Scale을 모든 설비 아이템이 공통으로 사용한다. 충돌은 해당 메시의 Simple Collision과 Root Scale을 따른다. 공통 `HeldTransform`은 일반 아이템과 동일하게 위치와 회전만 적용하고 Scale은 무시한다.
