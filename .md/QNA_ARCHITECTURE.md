# QnA — BathhouseSim Architecture

기존 Q1~Q26 답변은 [QNA_ARCHITECTURE_CUSTOMER_COMPLETED.md](QNA_ARCHITECTURE_CUSTOMER_COMPLETED.md)에 그대로 보존한다.

## Q27. 물 얼룩 제거 진행 중 장비 사용 입력을 어떻게 유지할까?

- A: 한 번 누르면 청소를 시작하고 유효 조건이 유지되는 동안 자동 진행
- B: LMB 장비 사용 입력을 누르고 있는 동안만 진행
- C: 누르는 즉시 제거하고 제거 시간은 표현에만 사용
- 권장안: B — 진행률과 실제 장비 사용 입력을 일치시키고 도구 상실 시 안전하게 중단할 수 있다.
- 답변: B

## Q28. 소지한 물걸레 또는 수건 바구니를 어떻게 내려놓을까?

- A: 각 물건의 지정된 원래 거치 위치에만 반환
- B: 유효한 바닥이면 원하는 위치에 내려놓기
- C: 별도 보관대 어디에나 반환
- 권장안: A — 기존 key rack 규칙과 같은 고정 반환 경계를 사용해 소실과 동선 차단을 막을 수 있다.
- 답변: B. G 장비 내려놓기 입력으로 응시 방향에 살짝 던져서 내려놓음.

## Q29. 세탁기와 건조기의 처리를 어떻게 시작할까?

- A: 첫 수건이 투입되면 즉시 자동 시작
- B: 기계의 별도 조작부를 기본 상호작용해 시작
- C: 용량이 가득 차거나 설정된 대기시간이 지나면 자동 시작
- 권장안: B — 플레이어가 투입 수량을 결정할 수 있고 수건 이동 입력과 기계 시작 입력을 서로 다른 대상으로 명확히 구분할 수 있다.
- 답변: B

## Q30. 깨끗한 수건 또는 반환 용량이 부족한 손님의 fallback은?

- A: 설정된 시간만 기다린 뒤 수건 없이 나머지 루틴 진행
- B: 설정된 시간만 기다린 뒤 무료 퇴장 루틴으로 전환
- C: 자원이 생길 때까지 계속 대기
- 권장안: A — 손님 흐름을 영구 정지시키지 않으면서 존재하지 않는 수건을 생성하거나 소실하지 않는다.
- 답변: A, 그리고 고객 내부의 만족도 수치는 하락.

## Q31. 물건을 든 상태에서 인게임 컴퓨터 사용을 시작할 수 있을까?

- A: 빈손일 때만 컴퓨터 사용 허용
- B: 물건을 든 상태 그대로 컴퓨터 사용 허용
- C: 기존 G 드랍 transaction으로 자동 내려놓기에 성공한 경우에만 컴퓨터 사용
- 권장안: A — key/mop/basket의 소유권과 드랍 실패 transaction을 건드리지 않고, held mesh가 모니터와 커서를 가리는 문제도 피할 수 있다.
- 답변: A

## Q32. LMB 입력 액션을 어떤 계약으로 통합할까?

- A: 기존 `IA_ComputerClick`과 `ComputerClickAction`을 범용 `IA_PrimaryUse`와 `PrimaryUseAction`으로 이관하고 현재 모드에 따라 컴퓨터 클릭 또는 장비 사용으로 라우팅
- B: 기존 컴퓨터 클릭 액션을 유지하고 별도 장비 사용 액션도 같은 LMB에 중복 매핑
- C: 일반 장비와 컴퓨터에 서로 다른 Input Mapping Context를 사용
- 권장안: A — LMB 물리 입력 하나에 소유자를 하나만 두고 Character는 모드만 라우팅할 수 있다.
- 답변: A

## Q33. 몽키스패너는 기존 단일 physical carry 슬롯을 사용할까?

- A: key, wet mop, towel basket과 같은 슬롯을 사용하며 E로 획득하고 G로 내려놓음
- B: 별도 무기 슬롯을 만들어 다른 물건과 동시에 소지
- C: 획득 후 영구 장착되어 내려놓을 수 없음
- 권장안: A — 현재 inventory/hotbar 없는 단일 소지품 계약을 유지할 수 있다.
- 답변: A

## Q34. 물걸레로 물 얼룩을 닦는 입력을 LMB로 옮길까?

- A: 물걸레를 들고 LMB를 누르는 동안 대상 유무와 무관하게 청소 중 상태와 물걸레 Actor의 반복 transform 애니메이션을 유지하고, 정면의 유효한 얼룩에만 실제 제거 진행 적용
- B: 청소는 기존 E hold를 유지하고 LMB는 무기에만 사용
- C: E와 LMB 모두 청소를 시작할 수 있게 허용
- 권장안: A — E는 월드 상호작용, LMB는 현재 장비 사용이라는 구분이 일관된다.
- 답변: A. 정면에 물 얼룩이 없어도 LMB Hold 동안 청소 중 상태와 몽키스패너 방식의 간단한 물걸레 움직임을 유지한다.

## Q35. 1인칭 몽키스패너 휘두르기 표현은 어떻게 만들까?

- A: 카메라 하위 weapon swing pivot에서 몽키스패너 Actor 자체를 curve 기반으로 움직임
- B: 별도 1인칭 팔 Skeletal Mesh와 공격 Montage를 추가함
- C: 보이는 휘두르기 없이 판정과 카메라 반응만 적용함
- 권장안: A — 현재 1인칭 팔 mesh가 없는 구조에서 이번 무기 범위를 가장 작게 유지할 수 있다.
- 답변: A

## Q36. 몽키스패너의 근접 피격 판정은 어떻게 수행할까?

- A: 공격 유효 구간 동안 몽키스패너 타격점의 이전·현재 위치 사이를 연속 sweep
- B: 무기가 가장 뻗은 시점에 카메라 위치·전방 기준 거리와 반경으로 단일 multi shape trace
- C: 휘두르는 동안 무기 collision overlap event만 사용
- 권장안: B — 무기 mesh와 공격 판정을 분리하고 1인칭 카메라 조준 기준으로 일관된 거리·범위를 제공할 수 있다.
- 답변: B

## Q37. LMB를 계속 누를 때 공격을 반복할까?

- A: LMB Started마다 한 번만 공격하고 공격 중 추가 입력은 무시
- B: LMB를 누르는 동안 공격을 자동 반복
- C: 공격 중 입력 한 번을 저장해 현재 공격 직후 한 번 더 실행
- 권장안: A — 첫 구현에서 공격 lifecycle과 중복 피해를 가장 명확하게 검증할 수 있다.
- 답변: A

## Q38. 손님이 죽지 않는 피해를 받았을 때 루틴을 어떻게 처리할까?

- A: 체력과 피격 표현만 갱신하고 현재 StateTree 루틴은 계속 진행
- B: 현재 루틴을 중단하고 즉시 퇴장 상태로 전환
- C: 현재 루틴을 중단하고 플레이어를 공격하는 상태로 전환
- 권장안: A — 이번 범위에 도주·전투 AI를 추가하지 않고 체력과 사망 경계를 먼저 완성할 수 있다.
- 답변: A

## Q39. 손님이 쓰러져 있는 동안 보유 자원과 예약을 어떻게 처리할까?

- A: key, towel handle, cash offer, queue와 facility 예약을 그대로 유지
- B: 쓰러질 때 모두 해제하고 일어난 뒤 필요한 자원을 다시 획득
- C: key와 towel만 월드에 떨어뜨리고 나머지 예약은 유지
- 권장안: A — 같은 손님이 남은 루틴을 이어갈 때 중간 transaction과 시설 소유권을 재구성하지 않아도 된다.
- 답변: A

## Q40. 체력이 0이 된 손님은 어떻게 복귀할까?

- A: Editor에서 조정 가능한 시간 동안 래그돌로 있다가 최종 위치에서 즉시 기립 상태로 복귀하고 남은 루틴 진행
- B: 래그돌 위치와 무관하게 쓰러지기 전 위치로 돌아가서 루틴 진행
- C: 플레이어가 별도 상호작용해야 기립하고 루틴 진행
- 권장안: A — 쓰러진 결과 위치를 유지하면서 별도 기상 애니메이션 없이 현재 요구사항을 구현할 수 있다.
- 답변: A

## Q41. 한 번의 휘두르기로 몇 개의 피해 가능 대상을 공격할까?

- A: 가장 먼저 맞은 손님 한 명만 피해
- B: 카메라 기준 공격 거리와 범위 안의 모든 피해 가능 대상에게 각각 한 번씩 피해
- C: Editor에서 최대 대상 수를 조정하고 기본값은 한 명
- 권장안: B — 조준 대상 하나를 선택하지 않고 실제 공격 volume 안의 모든 대상을 동일하게 처리할 수 있다.
- 답변: B. 플레이어가 의도하지 않은 대상도 범위와 거리 안에 있으면 함께 피격된다.

## Q42. 쓰러졌다 일어날 때 체력을 얼마나 회복할까?

- A: 최대 체력까지 전부 회복
- B: 체력 1로 회복
- C: Editor에서 회복 비율을 조정하고 기본값은 최대 체력의 100%
- 권장안: C — 현재는 완전 회복으로 사용하면서 이후 난이도 조정이 가능하다.
- 답변: C

## Q43. 손님이 쓰러져 있는 동안 session 단위 루틴 타이머를 어떻게 처리할까?

- A: check-in 대기, 전체 목욕 체류와 수건 대기 타이머를 일시정지하고 기립 후 남은 시간부터 재개
- B: 쓰러져 있는 동안에도 session 단위 타이머를 계속 진행
- C: 기립할 때 session 단위 타이머를 전체 시간으로 초기화
- 권장안: A — 쓰러져 있는 시간 때문에 check-in이나 전체 목욕 시간을 소비하지 않으며, 현재 국소 행동의 재시작은 Q45가 별도로 결정한다.
- 답변: A

## Q44. 이미 쓰러진 손님이 추가 공격을 받으면 어떻게 처리할까?

- A: 기립하기 전까지 추가 피해와 impulse를 모두 무시
- B: 추가 impulse를 적용하고 기립 대기 시간을 처음부터 다시 시작
- C: 추가 impulse만 적용하고 기존 기립 시간은 유지
- 권장안: A — 중복 래그돌 transaction과 무한 기립 지연을 막을 수 있다.
- 답변: A

## Q45. 기립 후 공격받던 당시의 행동을 어떻게 이어갈까?

- A: 보유 자원과 예약은 유지하고 당시 행동을 시작 지점부터 다시 실행
- B: 당시 행동을 완료된 것으로 처리하고 다음 루틴으로 진행
- C: 이동·몽타주·진행 시간을 쓰러지기 직전 지점부터 정확히 재개
- 권장안: A — 중단된 MoveTo와 Montage의 내부 진행 상태를 복원하지 않고도 루틴 일관성을 유지할 수 있다.
- 답변: A. 이미 완료된 원자적 transaction은 되돌리거나 중복 실행하지 않고, 중단 시점의 미완료 국소 행동만 시작 지점부터 다시 실행한다.

## Q46. Q45 A의 행동 재시작을 어느 계층에서 구현할까?

- A: C++ 루틴 실행 계층이 중단 일련번호와 pause/restart를 소유하고 기존 native StateTree Task를 재시작 가능하게 보강하며, 내장 MoveTo만 native restartable MoveTo Task로 교체
- B: 행동별 checkpoint와 복귀 transition을 `ST_CustomerRoutine` StateTree에 추가
- C: 전체 고객 루틴을 C++ state machine으로 이관하고 StateTree를 단일 Task로 축소
- 권장안: A — 현재 StateTree 계층과 domain transaction 경계를 유지하면서 행동별 복귀 분기를 추가하지 않고 중단된 이동·몽타주·시간 행동을 처음부터 재시작할 수 있다.
- 답변: A
